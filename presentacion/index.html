Secuencial

Un solo flujo de ejecución recorre toda la imagen fila por fila. Contra este tiempo medimos todas las versiones paralelas.

1 proceso · 1 threadfila –

El programa completa cada etapa sobre toda la imagen antes de empezar la siguiente: primero filtra, después detecta bordes, después posteriza y al final combina.

Son cuatro recorridos completos, siempre de arriba hacia abajo y de a una fila.

Memoria compartida

OpenMP

Un proceso con varios threads que ven la misma imagen. Cada thread se queda con un bloque de filas y todos trabajan a la vez.

1 proceso · memoria compartida
Threads

schedule(static): el trabajo de cada fila es parecido, así que el reparto se fija de antemano, sin coordinación extra.

Cada thread escribe en su propia zona, así que dos threads nunca modifican el mismo píxel. Al final de cada bucle hay una barrera implícita: nadie pasa a la etapa siguiente hasta que terminan todos.

// openmp.cpp, en cada una de las 4 etapas
#pragma omp parallel for schedule(static)
for (int fila = 0; fila < altoImagen; fila++) {
    for (int columna = 0; columna < anchoImagen; columna++) {
        // mismo cálculo que la versión secuencial
    }
}

MPI

Varios procesos, cada uno con su propia memoria. Para trabajar, primero hay que mandarles los datos y al final juntar lo que calcularon.

Procesos

El proceso 0 carga la imagen y la reparte con MPI_Bcast: primero el tamaño y después los píxeles. Cada proceso trabaja solo con sus filas, en dos pasos: primero filtra su bloque una sola vez y lo guarda; después aplica Sobel, posteriza y combina.

Al final, MPI_Gatherv junta los bloques en el proceso 0. Usamos Gatherv porque permite reunir bloques de distinto tamaño, cuando las filas no se dividen exacto.

Sobel necesita una fila vecina arriba y otra abajo, así que cada proceso filtra sus filas más esas dos y guarda todo en imagenFiltradaLocal. En la primera versión no se guardaba: el filtro se recalculaba para cada vecino de Sobel.

MPI + OpenMP

Híbrido

Dos niveles de reparto: MPI divide grupos de filas entre procesos y, adentro de cada proceso, OpenMP divide esas filas entre threads.

imagenCartoonen P0
1P0 carga la imagen 2MPI_Bcast 3filtrar bloque 4threads por proceso 5MPI_Gatherv
Procesos
Threads
Unidades de ejecución2 × 4 = 8
Filas por thread–

Se ejecuta con mpirun -np P y la cantidad de threads es por cada proceso. Con 2 procesos y 4 threads hay 8 unidades de ejecución.

Para la eficiencia contamos procesos × threads como unidades de ejecución. Usa el mismo esquema que MPI: cada proceso filtra su bloque una sola vez, y OpenMP reparte entre threads tanto el filtrado como el cómputo.

// hibrido.cpp: MPI ya asignó [filaInicial, filaFinal)
omp_set_num_threads(cantidadThreads);
#pragma omp parallel for schedule(static)
for (int fila = filaInicialFiltrado; fila < filaFinalFiltrado; fila++) { … } // filtrar bloque
#pragma omp parallel for schedule(static)
for (int fila = filaInicial; fila < filaFinal; fila++) { … } // Sobel, posterizado, combinación
MPI_Gatherv(resultadoLocal, …, imagenCartoon, …);

OpenMP y el híbrido quedan parejos, pero el híbrido usa el doble de unidades de ejecución.

Hallazgo 1

OpenMP, el más eficiente

Speedup de 2,70 a 2,75 con 4 threads y eficiencia cercana al 68 %. Los threads comparten la imagen y no hay que copiar datos entre procesos.

Hallazgo 2

El problema de MPI era el código

La versión inicial recalculaba el filtro hasta 9 veces por píxel y daba Speedup 0,63. Filtrando el bloque una sola vez pasó a 2,03 con 4 procesos.

Hallazgo 3

Híbrido: rápido, pero caro

Tiempo similar a OpenMP (0,98 s contra 0,96 s) con el doble de unidades: eficiencia cercana al 33 %. Más allá de 4 unidades, el trabajo cae en núcleos de eficiencia.

Hallazgo 4

5×5 pesa más

El filtro 5×5 analiza hasta 25 vecinos en lugar de 9 y subió el tiempo más que pasar de 3 a 9 niveles. En la versión inicial de MPI el efecto era mucho mayor: de 0,57 s a 1,42 s.

Paralelizar no es solo agregar threads o procesos: hay que medir, encontrar dónde se va el tiempo y corregirlo.

En nuestro caso, el bajo rendimiento de MPI no era la comunicación: era trabajo repetido. Corregido eso, OpenMP sigue siendo la opción más eficiente.
